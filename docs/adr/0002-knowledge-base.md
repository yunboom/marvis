# 知识库存在 Postgres 里：改动先进草稿，以变更请求按块三方合并，不用 git

知识库按 Karpathy LLM Wiki 的模式由智能体维护、人审核。页面和修订存在 Postgres（主线一张表，历史是只追加的修订表），正文拆成带稳定 id 的块；智能体用 `marvis kb` 的 `fetch` / `patch` 命令按块读写，改动先进一份草稿，草稿提交为变更请求，合并时页面没被别人动过就直接前进，动过则按块三方合并，同一块两边都改才算冲突。人只阅读、批注和审核，不在界面上编辑页面。维护工作在「知识库作业」里完成：作业是一段和执行智能体的聊天对话，不派任务。页面格式采用 OKF v0.2 页头和 OpenWiki 式的论断，对外只提供导出 OKF bundle。

## 考虑过的方案

- **一个工作区的知识库放进一个 git 仓库，内部托管或关联外部仓库**（一期做法）：放弃。块级的读写、批注跟着原句走、按块合并都要在 git 之上再做一层；托管仓库和外部仓库的切换、推送历史、权限映射是额外负担，而团队需要的只是可审核、可回滚的修订历史。
- **每次维护操作派发一个任务，任务绑定 PR、合并后自动完成**：放弃。知识任务会淹没任务列表；审核和留痕由变更请求承担，作业对话里还能当场纠正智能体。
- **成员在界面上直接编辑页面**：放弃。所有改动都由智能体按 Schema 写、附上论断和证据，审核时才看得清依据；成员要改就留批注交给智能体。
- **内置每日沉淀任务（每个工作区一条，不能删除）**：放弃。定时维护用普通的自动化，由「定时运行」开场白引导智能体创建，不给自动化加系统内置的特例。
- **按知识库另设负责人审批**：放弃。合并、关闭、回滚给知识库创建者和工作区 owner、admin，不在现有角色之外另开一套权限。

## 后果

- 一个变更请求只改一个知识库；审核页按页面展示文件卡片式的 diff，冲突时智能体把主线同步进草稿、在冲突块里解决。
- 合并变更请求不改动任何任务的状态；变更请求的来源按草稿反查，能跳回发起它的作业、对话、任务或自动化运行。
- 每个知识库作业只有一份草稿，作业和草稿用一张关联表记录，草稿本身不感知作业。
- 删除知识库在一个事务里删掉它的全部数据，提交后清理对象存储，界面不提供恢复。
- 不和外部 git 仓库双向同步；需要离线阅读或迁移时导出 OKF bundle，Obsidian 可以直接打开。
