# 知识库独立于任务系统：改动走会话和变更请求，所有知识库共用一个 git 仓库

知识库按 Karpathy LLM Wiki 的模式由智能体维护、人审核。我们让知识库完全不碰任务系统：批注纠错、沉淀、保鲜、知识合并、新建知识库都在知识库页里开一个和维护智能体的隐藏会话完成（做法同智能体创建智能体），每日沉淀任务是 `run_only` 的自动化，不建任务；所有改动（包括成员手动编辑）都产出变更请求，进入全局待审核队列，由工作区 owner/admin 合并。一个工作区的全部知识库放在同一个 git 仓库里，按目录隔离；仓库是内部托管或关联外部仓库二选一，不做镜像。页面格式采用 OKF v0.2 和 OpenWiki 的论断（Claims）文件。

## 考虑过的方案

- **每次操作派发一个任务，任务绑定 PR、合并后自动完成**：放弃。知识任务会淹没任务列表；内部托管的仓库没有 PR，硬凑一个 PR 实体只为复用状态联动；审核和留痕由变更请求队列就能承担，会话里还能当场纠正智能体。
- **每个知识库一个仓库，按库设负责人审批**：放弃。跨库操作要拆成多个变更请求、多组审批人；按库的负责人是在现有 owner/admin/member 角色之外另开一套权限。
- **每日任务读取全员对话（给 owner 加读取所有对话的权限，或给每日任务开特例）**：放弃。智能体调用接口时的身份是运行它的 runtime 的主人，owner 的权限会随跑在 owner 电脑上的任何智能体外溢给派任务的普通成员。每日任务只沉淀 runtime 主人自己能看到的对话。
- **另派一个智能体做预审、服务端扫描敏感信息**：放弃。产出变更请求的智能体在同一次会话里自查和过滤，确定性检查交给 `marvis kb lint` / `stale`。
- **多个知识库模板（开发、测试、产品、综合）**：放弃。star 数过千的开源实现都是一个团队库按页面类型组织，没有按角色分模板的先例；内置一份覆盖开发、测试、产品的 schema，用 `domains` 标签区分。

## 后果

- 每日沉淀任务每个工作区一条，给自动化新增系统内置标记：不能删除，没有知识库时不能启用，默认停用。
- 合并变更请求不改动任何任务的状态；会话、变更请求与任务之间只有链接。
- 一个变更请求可以同时改多个知识库，审核页按库分组展示 diff。
- 删除知识库是提交一次移除该目录的 commit，界面不提供恢复。
- 托管仓库切到外部仓库是单向的：推送完整历史后，外部仓库成为唯一仓库。
