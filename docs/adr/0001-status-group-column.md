# 状态分组存为独立字段 status_group，不复用 category

看板和状态库按四个状态分组排列状态（未开始 / 工作中 / 需介入 / 已结束），而平台行为由生命周期类型决定（未开始 / 已开始 / 已完成 / 已关闭）。我们给 `issue_status` 新增 `status_group` 列保存分组，`category` 保持原名继续表示生命周期类型；数据库约束限定两者只能是合法组合，内置状态的分组固定。分组只用于显示和智能体提示词，任何行为判断都不读它。

## 考虑过的方案

- **把 `category` 改名为生命周期类型，新建一个叫 `category` 的分组字段**：放弃。本仓库 fork 自上游，上游持续新增 `entry.Category == issuestatus.CategoryDone` 这类判断；复用同名字段后，上游代码合进来照样编译通过，却拿分组当生命周期判断，结果悄悄出错。改名本身还要动几十个 Go / SQL / 前端文件和 API 字段，每次同步上游都冲突。
- **只存一个「需介入」布尔标记，分组由它和生命周期类型推导**：可行，但分组要靠推导才能得到，查询和筛选都不直接；完整的分组字段配合组合约束，同样不会出现两个字段矛盾的情况。
- **把分组放进工作区设置、只改前端**：后端和智能体提示词拿不到分组，新建状态也要两次请求，无法原子完成。

## 后果

- 已开始的状态可以在工作中和需介入之间切换，生命周期类型创建后仍不可改。
- 后端按生命周期类型排序，工作中和需介入同属已开始：前端在任一组拖动排序时，要把另一组的现有顺序一起提交。
- 同步上游时，上游新增的状态插入路径（迁移、种子数据、工作流模板）需要带上 `status_group`；没带时数据库触发器按生命周期类型给默认分组。
