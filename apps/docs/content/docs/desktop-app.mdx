Marvis Desktop is available for macOS, Windows, and Linux. It uses the same account and workspace data as the web app, but it manages the daemon on your machine automatically and keeps a separate set of tabs for each workspace.

## Desktop and web

| | Web | Desktop |
| --- | --- | --- |
| How you open it | Browser | Install the desktop app |
| Workspace tabs | Uses browser tabs | Each workspace keeps its own set of tabs |
| Daemon | Install and start the CLI separately | Started by the app automatically after sign-in |
| Updates | Refresh the page | Updated through the desktop app |

Web is more convenient for a quick look or on a shared computer.

You can be signed in to both at the same time. As long as they connect to the same Marvis service, the data they show is shared.

## Installation

<Steps>
<Step>
Pick the installer that matches your OS and CPU architecture from the [Marvis downloads page](https://marvis.ai/download):

| Platform | Installer |
| --- | --- |
| macOS | `.dmg` |
| Windows | `.exe` |
| Linux | `.AppImage`, `.deb`, or `.rpm` |
</Step>
<Step>
After installing, [connect Desktop to a Marvis server](#connecting-to-a-server) and sign in. Once signed in, Desktop starts its own bundled Marvis CLI and detects the AI coding tools already installed on the machine.
</Step>
</Steps>

<Callout type="info">
The CLI bundled with Desktop only serves the app's managed runtime. If you also want to run commands like `marvis issue` in a terminal, install the CLI separately following [step 2 of the quickstart](/cloud-quickstart#2-connect-a-computer).
</Callout>

## Desktop tabs

Desktop saves tabs per workspace. For example, if you open three issues in workspace A and switch to workspace B, you see B's own tabs; switch back to A and the three earlier tabs are still there.

<DesktopTabsDemo />

A given resource opens only once in the current workspace. Tabs can be reordered, pinned, and closed, and each keeps its own forward/back history and scroll position. Pinned tabs sit at the left end and have no close button; unpin a tab to close it. Opening another page from a pinned tab opens a new tab, and the pinned tab stays where it is. Clicking or pasting an app link for this deployment opens it directly in a tab instead of jumping to the browser.

Logging out clears every tab saved on the machine, so the next person to sign in never sees pages left behind by the previous account.

## Built-in daemon

After sign-in, Desktop creates a dedicated CLI profile for the current Marvis service and uses it to start the daemon. The profile lives at:

```text
~/.marvis/profiles/desktop-<host>/
```

It never reads or overwrites the default profile you use in the terminal. If you also start another daemon manually, Marvis shows them as separate runtimes.

You can check runtime status and logs in Desktop's settings. If a tool isn't detected, first confirm it runs in a regular terminal and is logged in, then restart Desktop's daemon.

## Updating Desktop

Auto-update is on by default. The app checks for and downloads new versions in the background; once a download finishes you can restart to install immediately or let it install on the next quit. Under **Settings → Updates** you can turn off automatic checks or check for new versions manually.

Updates are distributed per OS and CPU architecture:

- Windows arm64 and macOS x64 (Intel) each use their own update feed;
- all other architectures use the default feed;
- the app matches the update feed automatically, so no manual selection is needed;
- on Linux, auto-update only works for `.AppImage`; update `.deb` and `.rpm` by installing a new package over the old one;
- if auto-update fails, likewise install over the top with the matching installer from the downloads page.

## Connecting to a server

Desktop connects to the Marvis server, which is the backend. Deploy the web app alongside it: Google and Feishu sign-in and **Copy link** go through the web app.

### First launch

Without a configured server, Desktop shows **Connect to a Marvis server**.

1. Pick a server under **Servers on your local network**, or enter an address. The default address is `http://marvis.local:13840`.
2. For an address, click **Test connection**. Desktop shows the server name and version, or the reason it can't connect.
3. Click **Continue**, check the address on the confirmation page, then click **Connect**.
4. Sign in.

The list updates as servers appear and disappear. **Search again** rescans the network. The computer and the server must be on the same network. A server that runs on this computer is marked **This computer**. A server whose version is too old is listed but can't be selected.

Desktop waits for your confirmation before connecting and never signs in on its own. A server that uses HTTP is not encrypted, and the confirmation page says so.

Desktop saves the chosen server as `server.json` in its app-data folder:

| Platform | Path |
| --- | --- |
| macOS | `~/Library/Application Support/Marvis/` |
| Linux | `~/.config/Marvis/` |
| Windows | `%APPDATA%\Marvis\` |

### Switching servers

Open **Settings → This device → Server**. The page shows:

- the current server with its name, address, and connection status;
- the other servers found on the local network, each with **Switch**;
- an **Other address** field with **Test connection** and **Switch**.

Switching signs you out of the current account. Desktop asks you to confirm, saves the new server, and opens the sign-in page. The built-in daemon uses the profile of the new server automatically.

The setting applies to this computer only.

### When the connection drops

- When the server stops responding, a banner at the top of the main area says the connection is lost and Desktop is reconnecting.
- After repeated failures, the banner says the server can't be reached and offers **Retry** and **Switch server**. Desktop keeps checking and goes back online by itself when the server returns.
- A server picked from the local network list is saved by its IP address. When that address stops answering and the same server, matched by its instance ID, appears on the local network at a new IP, Desktop switches to the new address and says it reconnected.
- When a different server answers at the saved address, Desktop shows **A different server is at this address** and does not switch on its own. Choose **Keep waiting** or **Switch server**.

### Without a web app

When the server has no web address, or the address is `localhost`, Desktop treats it as having no web app. A deployed server should not be in this state; it comes up in local development:

- the sign-in page hides the Google button. The Feishu button stays when Feishu login is set up on the server and `MARVIS_LARK_LOGIN_DESKTOP_REDIRECT_URI` is set to a backend callback address registered in the Feishu developer console. Desktop then opens Feishu sign-in in the browser and returns to the app when it finishes. Otherwise only email-code login remains;
- **Copy link** produces a `marvis://open?...` link, which opens in Desktop on any computer where Desktop is installed and connected to the same server.

## Presetting the server with desktop.json

An operator can preset the server for a computer. Desktop reads the preset only while no server has been chosen in the app. It connects without showing the connection page and never writes the file.

Create `desktop.json` inside the `.marvis` directory of your home directory with this content:

```json
{
  "schemaVersion": 1,
  "apiUrl": "https://api.example.com"
}
```

<Tabs groupId="os" persist items={["macOS / Linux", "Windows"]}>
<Tab value="macOS / Linux">

| Platform | Path |
| --- | --- |
| macOS | `/Users/<you>/.marvis/desktop.json` |
| Linux | `/home/<you>/.marvis/desktop.json` |

</Tab>
<Tab value="Windows">

The file path is `C:\Users\<you>\.marvis\desktop.json`.

Notepad and PowerShell redirection easily produce a file Desktop can't read (see [Windows: check the filename and encoding](#windows-check-the-filename-and-encoding)), so create it from PowerShell in one step:

```powershell
$dir = "$env:USERPROFILE\.marvis"
New-Item -ItemType Directory -Force $dir | Out-Null
$json = @'
{
  "schemaVersion": 1,
  "apiUrl": "https://api.example.com"
}
'@
[System.IO.File]::WriteAllText("$dir\desktop.json", $json)
```

</Tab>
</Tabs>

These are the default locations. If your home directory has been moved or redirected, use its actual path.

<Callout type="warning">
This is **not** the CLI's `~/.marvis/config.json`, and the key names differ: the CLI uses `server_url`, Desktop uses `apiUrl`. Desktop never reads the CLI's config; it manages a separate daemon profile under `~/.marvis/profiles/desktop-<host>/`. Editing `config.json` does not change which server Desktop connects to.
</Callout>

`apiUrl` is the backend's public address; it is required and must use `http` or `https`. The other two URLs can be omitted, and Desktop derives them automatically:

- `wsUrl`: swaps the `apiUrl` scheme to `ws` or `wss` and appends `/ws` to the path;
- `appUrl`: strips the `api.` prefix when the host starts with `api.` and has at least three labels (`api.example.com` → `example.com`); otherwise it stays the same as `apiUrl`.

A preset always has a web app address, derived when `appUrl` is omitted.

Usually `apiUrl` alone is enough. Override explicitly only when the derivation doesn't match your deployment; the three common cases:

- the web app and the API are on different domains;
- WebSocket is deployed separately;
- the host doesn't fit the prefix-stripping convention (two-label hosts like `api.local` keep their prefix).

```json
{
  "schemaVersion": 1,
  "apiUrl": "https://api.example.com",
  "appUrl": "https://app.example.com",
  "wsUrl": "wss://ws.example.com/socket"
}
```

Restart Desktop after saving; the file is read once at startup. The two failure modes look different:

- **File not found** (wrong directory, or a filename that isn't exactly `desktop.json`): Desktop shows the connection page and no error. So if Desktop still asks you to connect to a server and shows no configuration error, the file is not where Desktop is looking.
- **File found but invalid** (JSON, version, or URLs): Desktop shows a configuration error.

Delete the file and restart to return to the connection page. If a server was chosen in the app, also delete `server.json` from the app-data folder.

<Callout type="warning">
Desktop can only connect to addresses reachable from both the browser and the executing machine. If a remote self-hosted instance doesn't use HTTPS or doesn't proxy WebSocket, Desktop can't establish a connection; see the [self-host quickstart](/self-host-quickstart#remote-access) for the full configuration.
</Callout>

### Windows: check the filename and encoding

Two common ways of writing the file on Windows produce one Desktop can't read:

- **Notepad appends `.txt`.** Saving as `desktop.json` can produce `desktop.json.txt`, which Desktop treats as not found. Turn on file name extensions in Explorer, or pick *All files* in the save dialog. To see the real filename, run `Get-ChildItem "$env:USERPROFILE\.marvis" -Filter "desktop.json*"` in PowerShell; the `Name` column must read exactly `desktop.json`.
- **PowerShell redirection writes UTF-16 or a BOM.** `> desktop.json` and `Out-File` can produce an encoding that fails to parse, which surfaces as a configuration error.

The PowerShell command in the Windows tab above avoids both.

## Windows Defender flags Marvis as a virus

Windows Security reports a threat such as `Trojan:Script/Wacatac.B!ml` and quarantines a file inside the Desktop installation. The affected item is normally the bundled CLI, not the app executable:

```text
C:\Users\<you>\AppData\Local\Programs\@marvisdesktop\resources\app.asar.unpacked\resources\bin\marvis.exe
```

This is a false positive. The `!ml` suffix means the verdict came from Defender's machine-learning heuristics rather than a malware signature. Marvis's Windows builds are not Authenticode code-signed yet, and a freshly published unsigned binary that starts background processes and opens network connections is the kind of binary those heuristics readily score as suspicious. Every Windows artifact is built by GitHub Actions from the public source in this repository.

You can verify it yourself: each GitHub release publishes a `checksums.txt` covering every CLI archive.

```powershell
Get-FileHash .\marvis-cli-<version>-windows-amd64.zip -Algorithm SHA256
```

Compare the hash with the matching line in `checksums.txt` on the [latest release](https://github.com/yunboom/marvis/releases/latest).

Fix it in three steps:

<Steps>
<Step>
Restore the quarantined file: Windows Security → *Virus & threat protection* → *Protection history* → select the Marvis item → *Actions* → *Restore*.
</Step>
<Step>
Add an exclusion so it isn't quarantined again: *Virus & threat protection* → *Manage settings* → *Exclusions* → *Add an exclusion* → *Folder*, and add both:

- `%LOCALAPPDATA%\Programs\@marvisdesktop`
- `%APPDATA%\Marvis`

Both paths matter: when the bundled CLI goes missing, Desktop downloads a replacement into `%APPDATA%\Marvis\bin`, so excluding only the install folder leaves you in a loop where the replacement gets quarantined too.
</Step>
<Step>
Report the false positive to Microsoft at [Microsoft Security Intelligence — submit a file](https://www.microsoft.com/en-us/wdsi/filesubmission), choosing *Software developer* and *Incorrectly detected as malware*. That is what gets the detection withdrawn for every user, usually within a few days.
</Step>
</Steps>

<Callout type="warning">
Only add these exclusions if you installed Marvis from the [downloads page](https://marvis.ai/download) or [GitHub releases](https://github.com/yunboom/marvis/releases) and the checksum matches. An exclusion disables real-time protection for everything in that folder.
</Callout>
