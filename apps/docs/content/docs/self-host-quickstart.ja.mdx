Marvis のセルフホストは 2 つの部分に分かれます。

| 構成要素 | 実行するもの | 置く場所 |
|---|---|---|
| **Marvis サービス** | Web、API、PostgreSQL | Docker をインストールした 1 台のマシン |
| **実行用コンピュータ** | Marvis デーモンと AI コーディングツール | 開発者が実際に作業するコンピュータ |

両者は同じマシンでも、別々のマシンでも構いません。セルフホストで置き換えるのは Marvis Cloud の部分だけです。

このページでは Docker Compose を使います。Kubernetes でのデプロイは、リポジトリの [Self-hosting guide](https://github.com/yunboom/marvis/blob/main/SELF_HOSTING.md#kubernetes-deployment-alternative) を参照してください。

## 始める前に

Marvis サービスを実行するマシンには次が必要です。

- Docker Engine または Docker Desktop（`docker compose` が実行できること）
- Git、Make、curl、OpenSSL
- ポート `3000` と `13840` が空いていること

まず Docker と Compose が使えることを確認します。

```bash
docker info
docker compose version
```

Marvis は Compose v2（`docker compose`）を使います。旧版の `docker-compose` v1 はサポートされません。

実行用コンピュータには、Claude Code、Codex、Cursor などの [AI コーディングツール](/providers)を最低 1 つインストールし、ログインしておく必要があります。Marvis CLI はステップ 5 でインストールします。

## 1. Marvis を起動する

サービスを実行するマシンで次を実行します。

```bash
git clone --depth 1 https://github.com/yunboom/marvis.git
cd marvis
make selfhost
```

初回実行時、`make selfhost` は次を行います。

1. `.env.example` から `.env` を作成する
2. `JWT_SECRET`、PostgreSQL パスワード、`MARVIS_VCS_SECRET_KEY`（セルフホストの Git 連携用の暗号化キー）をランダム生成する
3. PostgreSQL、Marvis backend、Marvis frontend のイメージを取得する
4. 永続化ボリュームを作成し、3 つのコンテナを起動する
5. backend がヘルスチェックに応答し始めるまで待機する

2 回目以降の `make selfhost` は既存の `.env` とボリュームをそのまま使い、シークレットを再生成しません。

<Callout type="info">
`make selfhost` は公開済みのイメージを取得し、checkout 中のコードをビルドしません。ローカルのソースを試すには `make selfhost-build` を使ってください。

公開済みのイメージは最新の **release タグ** を追跡しますが、単なる `git clone` でチェックアウトされるのは `main` で、通常リリースより先行しています。この checkout から何かをビルドする場合（CLI、または `make selfhost-build` によるイメージ）は、先に対応する release タグへ切り替えて、ビルドしたバイナリと稼働中のコンテナのバージョンを揃えてください:

```bash
git fetch --tags --depth 1
git checkout $(git tag -l 'v*' --sort=-v:refname | head -1)
```
</Callout>

## 2. サービスの準備完了を確認する

コンテナの状態を確認します。

```bash
docker compose -f docker-compose.selfhost.yml ps
```

`postgres` が `healthy`、`backend` と `frontend` が実行中であることを確認します。続いて backend、データベース、migration をチェックします。

```bash
curl -fsS http://localhost:13840/readyz
```

期待されるレスポンスは次のとおりです。

```json
{"status":"ok","checks":{"db":"ok","migrations":"ok"}}
```

backend コンテナは起動のたびにデータベースの migration を実行してからサービスを開始するため、migration コマンドを手動で実行する必要はありません。

## 3. アクセス方法を選ぶ

### ローカルアクセス

[http://localhost:3000](http://localhost:3000) をそのまま開きます。後で `marvis setup self-host` を実行するときも、URL を渡す必要はありません。

### リモートアクセス

Docker Compose はデフォルトで `3000` と `13840` を `127.0.0.1` だけにバインドします。`0.0.0.0` に変えて公開インターネットへ直接さらさず、HTTPS 付きのリバースプロキシを使ってください。

以下では 2 つのドメインを例にします。

- `app.example.com`: Marvis Web
- `api.example.com`: API、ヘルスチェック、デーモン接続

まず `.env` に公開 URL を設定します。

```bash
FRONTEND_ORIGIN=https://app.example.com
MARVIS_APP_URL=https://app.example.com
MARVIS_PUBLIC_URL=https://api.example.com
```

この構成ではブラウザのトラフィックがすべて app ドメインを経由し、cookie がドメインをまたがないため、`COOKIE_DOMAIN` の設定は不要です。ブラウザに api ドメインへ直接アクセスさせる場合は設定が必須です。[環境変数](/environment-variables)を参照してください。

次に DNS を設定し、Caddy でローカルポートをプロキシします。

```text
app.example.com {
    # ブラウザの WebSocket は backend へ直接渡す
    @ws path /ws /ws/*
    handle @ws {
        reverse_proxy 127.0.0.1:13840 {
            flush_interval -1
        }
    }

    # 残りのパスは frontend へ。API とログインのリクエストを転送する
    handle {
        reverse_proxy 127.0.0.1:3000
    }
}

api.example.com {
    reverse_proxy 127.0.0.1:13840 {
        flush_interval -1
    }
}
```

すべてのトラフィックを**単一オリジン**（1 つのドメイン、または 1 台のホストに 1 つのポートで、小規模サーバーで一般的な構成）で扱いたい場合は、デーモンが依存するパスを backend に明示的に転送し、残りを frontend に任せます:

```text
marvis.example.com {
    # CLI の到達確認: `marvis setup` は <server-url>/health に GET を送り 200 を要求する。
    # 古い frontend はこのパスを転送しないため、backend に直接ルーティングする
    handle /health {
        reverse_proxy 127.0.0.1:13840
    }

    # ブラウザの realtime WebSocket——web イメージは WS アップグレードを proxy できないため backend へ直接
    handle /ws {
        reverse_proxy 127.0.0.1:13840 {
            flush_interval -1
        }
    }

    # デーモンの長時間接続: {server-url}/api/daemon/ws にダイヤルします（/ws ではない）。
    # このルートがないとハンドシェイクが失敗し、デーモンは通知なくポーリングへフォールバックします
    handle /api/daemon/ws {
        reverse_proxy 127.0.0.1:13840 {
            flush_interval -1
        }
    }

    # 残りのパスは frontend へ。API とログインのリクエストを転送する
    handle {
        reverse_proxy 127.0.0.1:3000
    }
}
```

単一オリジンでは、2 つの URL をどちらもそこに向けます（`.env` の `FRONTEND_ORIGIN` と `MARVIS_APP_URL`、および `marvis setup self-host` の `--server-url` と `--app-url`）。

Caddy が TLS 証明書を取得し、WebSocket を転送します。`.env` を変更したら、`up -d` でコンテナを作り直して新しい設定を反映します。

```bash
docker compose -f docker-compose.selfhost.yml up -d
curl -fsS https://api.example.com/readyz
curl -fsS https://app.example.com/api/config | grep -o '"daemon_server_url":"[^"]*"'
```

最後のコマンドは `daemon_server_url`（デーモンが API に接続するための URL）を出力します: `MARVIS_DAEMON_SERVER_URL` が設定されていればそれを、次に `MARVIS_PUBLIC_URL`、どちらも未設定ならアプリ URL（`MARVIS_APP_URL`、未設定なら `FRONTEND_ORIGIN` にフォールバック）を使います。`MARVIS_APP_URL` と `FRONTEND_ORIGIN` のどちらも未設定の場合、`MARVIS_DAEMON_SERVER_URL` や `MARVIS_PUBLIC_URL` が設定されていてもこのフィールドはレスポンスから丸ごと省略されます（上の grep は何も出力しません）。`localhost` と出力される場合は `.env` がまだローカルのデフォルトのままです: `.env.example` からコピーした `${FRONTEND_PORT}` 参照に頼らず、`FRONTEND_ORIGIN` と `MARVIS_APP_URL` を公開 URL として明示的に設定し、コンテナを作り直してください。

<Callout type="warning">
`docker compose restart` は既存のコンテナを再起動するだけで、`.env` を読み直しません。設定を変更した後に `.env` を読み直すには、`docker compose -f docker-compose.selfhost.yml up -d` を実行してください。
</Callout>

## 4. ログインしてワークスペースを作成する

ローカルの `http://localhost:3000`、または先ほど設定した `https://app.example.com` を開き、メールアドレスを入力して認証コードをリクエストします。

デフォルトではメールサービスは設定されていません。コードをリクエストしたら、backend のログから読み取ります。

```bash
docker compose -f docker-compose.selfhost.yml logs backend \
  | grep "Verification code"
```

ログには次のような行が出力されます。

```text
[DEV] Verification code for you@example.com: 123456
```

コードを入力して、最初のワークスペースを作成します。Resend または SMTP を設定すると認証コードはメールで送信され、メンバーがコンテナログを読む必要はなくなります。詳しくは[ログインとサインアップ設定](/auth-setup)を参照してください。

<Callout type="warning">
セルフホストのデプロイはデフォルトで `APP_ENV=production` を使い、固定の認証コードは有効になりません。公開インスタンスで `MARVIS_DEV_VERIFICATION_CODE` を設定しないでください。
</Callout>

## 5. 実行用コンピュータを接続する

以下のコマンドは **AI コーディングツールを実行するコンピュータ**で実行します。Docker を実行しているサーバーとは限りません。

<Callout type="warning">
作業はデーモンを実行しているユーザーの全権限で動作し、そのユーザーが読み書きできるものはすべて読み書きできます。個人アカウントではなく、専用の Unix ユーザー、コンテナ、または VM でデーモンを実行してください。[セキュリティモデル](/security-model)を参照してください。
</Callout>

まず Marvis CLI をインストールします。

**macOS / Linux**

```bash
curl -fsSL https://raw.githubusercontent.com/yunboom/marvis/main/scripts/install.sh | bash
```

**Windows PowerShell**

```powershell
irm https://raw.githubusercontent.com/yunboom/marvis/main/scripts/install.ps1 | iex
```

Marvis サービスがこのコンピュータでも動いている場合は、次を実行します。

```bash
marvis setup self-host
```

Marvis サービスが別のマシンで動いている場合は、先ほど設定した 2 つの URL を渡します。

```bash
marvis setup self-host \
  --server-url https://api.example.com \
  --app-url https://app.example.com
```

このコマンドはまず `<server-url>/health` を確認し、次にブラウザを開いてログインを完了します。ログイン後はローカルに認証情報を保存し、デーモンを起動します。このステップで `Server not reachable` エラーが出る場合、`/health` のプローブが 200 を取得できなかったことを意味します: プロキシがすべてのトラフィックをこのパスを転送しない古い frontend に向けているか、プロキシが `/health` を backend にルーティングしていないか、あるいは DNS・TLS・ファイアウォール・タイムアウト・backend からの 5xx といったより下位の障害です。詳細は[トラブルシューティング](/troubleshooting#marvis-setup-がサーバーに到達できないと報告する)を参照してください。

接続状態を確認します。

```bash
marvis daemon status
```

正常であれば、出力に次が表示されます。

- `Daemon: running`
- `Agents` にこのマシンにインストール済みの AI コーディングツールが並ぶ
- `Workspaces` が `0` より大きい

## 6. 最初の実行を完了する

Marvis に戻ります。ランタイム一覧にオンラインのランタイムが表示されたら、エージェントを作成し、最初のタスクを割り当てます。

実行ログが完了になり、タイムラインにエージェントの返信が現れれば、セルフホストのサービス、実行用コンピュータ、AI コーディングツールがつながっています。詳しい手順は[クイックスタート](/cloud-quickstart)のステップ 3〜5 を参照してください。

## ローカルネットワーク検出

ローカルネットワーク検出を使うと、同じネットワーク上の Desktop と CLI が、アドレスを入力しなくても Marvis サーバーを見つけられます。オフィスの Mac など、チームで 1 台のマシンを共有する場面に向いています。

検出機能はデフォルトでオフです。`.env` に `MARVIS_LAN_DISCOVERY=true` を設定し、`make start` または `make server` でソースからサーバーを起動します。サーバーは次を広告します:

- サービス `_marvis._tcp`。ポートはバックエンドのポートで、デフォルトは `13840` です。
- ホスト名 `marvis.local`。ネットワーク上の別の Marvis サーバーがすでに使っている場合、このサーバーは `marvis-2.local` になり、バックエンドのログに実際の名前が記録されます。

`.env` の次の 2 つの変数は省略できます:

| 変数 | 内容 |
| --- | --- |
| `MARVIS_LAN_DISCOVERY` | `true` にすると広告します。デフォルトはオフです。 |
| `MARVIS_LAN_NAME` | クライアントに表示するサーバー名。デフォルトはコンピュータ名です。 |

クライアントは見つけたサーバーを一覧にするだけです。確認するまで、接続もサインインも行いません。何も見つからない場合は、アドレスに `http://marvis.local:13840` を入力します。

<Callout type="warning">
Docker では、ローカルネットワーク検出は使えません。Docker Desktop はローカルネットワークにマルチキャストを送れないため、バックエンドのイメージは `MARVIS_LAN_DISCOVERY` をデフォルトで `false` にしています。`docker-compose.selfhost.yml` と Helm でも同じです。Docker デプロイには、アドレスを入力すれば接続できます。検出を使うには、サーバーをソースから実行します。
</Callout>

macOS は初回に、サーバー側と各クライアント側でローカルネットワークの許可を求めます。許可してください。

### Desktop と Web アプリ

Desktop に必要なのはバックエンドだけです。Web アプリは必須ではありません。同じネットワークで Web アプリも提供するには、`.env` に `MARVIS_APP_URL=http://marvis.local:3000` を設定し、Google と Feishu のログインのコールバックアドレスとして `http://marvis.local:3000/auth/callback` を登録します。

Web アドレスがない場合、または `localhost` の場合、クライアントは Web アプリがないものとして扱い、Desktop は Google のボタンを非表示にします。ただし、サーバーが動いているコンピュータ上の CLI では `localhost` の Web アドレスを使えます。詳しくは[デスクトップアプリ](/desktop-app#サーバーへの接続)を参照してください。

Desktop の Feishu ログインは Web アプリがなくても使えます。Feishu 開発者コンソールで、リダイレクト URL として `http://marvis.local:13840/auth/lark/desktop-callback` も登録します。このコールバックはバックエンドが直接処理するため、バックエンドだけを動かしている場合も Desktop に Feishu のボタンが残ります。このアドレスは、サーバーが広告するホスト名とバックエンドのポートから組み立てられます。サーバーが `marvis-2.local` として広告されている場合や別のポートを使う場合は、対応するアドレスを登録します。ローカルネットワーク検出がオフの場合（デフォルト）は、登録したアドレスを `.env` の `MARVIS_LARK_LOGIN_DESKTOP_REDIRECT_URI` に設定します。

#### Feishu 招待

ワークスペースの owner と admin は Feishu のグループや個人に招待カードを送れます。カードをクリックした人はワークスペースに参加します。招待には Feishu ログインアプリ（`MARVIS_LARK_LOGIN_APP_ID` / `MARVIS_LARK_LOGIN_APP_SECRET`）をそのまま使います。Feishu 開発者コンソールで、このアプリに次を設定します:

1. ボット機能を有効にする。
2. 次の 6 つの権限を申請する: `im:message:send_as_bot`、`im:chat:readonly`、`contact:user.id:readonly`、`contact:contact.base:readonly`、`contact:user.base:readonly`、`contact:user.email:readonly`。
3. イベントとコールバックで、コールバックの受信方式を長時間接続（long connection）にし、`card.action.trigger` コールバックを追加する。
4. 利用可能範囲を、招待する可能性のある全員が含まれるように設定する。範囲外の人はカードから参加できません。
5. アプリの新しいバージョンを公開する。

続いて `.env` に `MARVIS_LARK_INVITE_ENABLED=true` を設定し、`docker compose -f docker-compose.selfhost.yml up -d` を実行します。任意で `MARVIS_DESKTOP_DOWNLOAD_URL` を設定すると、カードに「下载 Marvis」（Marvis をダウンロード）ボタンが表示されます。Marvis Cloud のシート容量が有効な場合、Feishu 招待は使えません。

<Callout type="warning">
Feishu 招待は、1 つの Feishu アプリにつき 1 つのデプロイでのみ有効にしてください。Feishu はカードのクリックをアプリの長時間接続のいずれか 1 つに届けるため、スイッチがオフのデプロイに届いたクリックは失われます。
</Callout>

### CLI

ターミナルで `--server-url` を付けずに `marvis setup self-host` を実行すると、ネットワークを約 3 秒検索し、見つかったサーバーを一覧にします。このコンピュータで動いているサーバー（`http://localhost:13840`）が先頭に表示されてあらかじめ選択され、その次に Desktop が使っているサーバーが表示されます。最後の項目でアドレスを手入力できます。

選択したサーバーに Web アプリがない場合、コマンドはブラウザを開きません。Desktop の **設定 → API トークン** でトークンを作成し、`marvis login --token` を実行します。

`--server-url` や `MARVIS_SERVER_URL` を指定した場合、CLI の設定にサーバーアドレスがすでにある場合、またはターミナル以外で実行した場合、コマンドの動作はこれまでと同じです。

## よく使う管理コマンド

以下のコマンドはすべて `marvis` リポジトリのディレクトリで実行します。

```bash
# 状態を確認する
docker compose -f docker-compose.selfhost.yml ps

# backend のログを追う
docker compose -f docker-compose.selfhost.yml logs -f backend

# .env の変更を反映する
docker compose -f docker-compose.selfhost.yml up -d

# サービスを停止する（ボリュームは保持）
docker compose -f docker-compose.selfhost.yml down
```

公開済みの最新イメージへアップグレードします。

```bash
git pull --ff-only
docker compose -f docker-compose.selfhost.yml pull
docker compose -f docker-compose.selfhost.yml up -d
curl -fsS http://localhost:13840/readyz
```

Docker Compose 構成のアップグレード方法は2通りあります。既存の構成では**同じ結果**になります — `Makefile` の `selfhost` ターゲットは同じ `docker compose pull` + `up -d` を実行し、加えて `.env` が無ければ生成し、`/health` を待ってからステータスの要約を表示します。好きな方を使ってください。

```bash
cd marvis
git pull
make selfhost
```

```bash
cd marvis
git pull
docker compose -f docker-compose.selfhost.yml pull
docker compose -f docker-compose.selfhost.yml up -d
```

### `git pull` が実際に更新するもの

`git pull` が更新するのは **`docker-compose.selfhost.yml` そのもの**です — 新しい環境変数、新しいサービス、変更された healthcheck。新しい Marvis のバージョンを取得する仕組み**ではありません**。

実際に動くバージョンを決めるのは `docker compose pull` で、そのタグが今どのイメージを指しているかを GHCR に問い合わせます。したがって数か月更新していない checkout でも今日の `latest` イメージを取得できますし、逆に `git pull` だけではイメージを取得してコンテナを作り直すまで何も変わりません。

<Callout type="warning">
**`MARVIS_IMAGE_TAG` を固定している場合、どちらのコマンドでもアップグレードされません。** 両方のイメージが `${MARVIS_IMAGE_TAG:-latest}` として解決され（`docker-compose.selfhost.yml`：`services.backend.image`、`services.frontend.image`）、`.env.example` は `MARVIS_IMAGE_TAG=latest` を同梱しています。`.env` で特定のリリースに固定していると、`pull` は同じタグを取り直すだけで、古いバージョンのままです — エラーも警告も出ません。アップグレード前に確認してください。

```bash
grep MARVIS_IMAGE_TAG .env
# MARVIS_IMAGE_TAG=v0.4.5   ← 固定されている: 先に latest（または希望のリリース）へ変更する
```
</Callout>

### `.env` は上書きされません

`make selfhost` が `.env` を生成するのは、ファイルが**存在しない**ときだけです。既存の構成で再実行しても、`JWT_SECRET`、Postgres のパスワード、メール設定、`FRONTEND_ORIGIN` はそのまま残ります。

### 先に Postgres をバックアップする

migration は前方向のみで巻き戻せないため、大事な環境をアップグレードする前にダンプを取ってください。

```bash
docker compose -f docker-compose.selfhost.yml exec -T postgres \
  pg_dump -U marvis marvis > marvis-backup.sql && gzip marvis-backup.sql
```

<Callout type="warning">
**`pg_dump` を直接 `gzip` にパイプしないでください。** シェルはパイプラインの**最後**のコマンドの終了ステータスを返すため、`pg_dump … | gzip > backup.sql.gz` はダンプが失敗しても `0` で終了し、形式としては完全に正当な、中身が空の20バイトのアーカイブが残ります。先にファイルへリダイレクトすれば `pg_dump` 自身の終了ステータスが効くようになり、`&&` は実際に成功したダンプだけを圧縮します。
</Callout>

`POSTGRES_USER` / `POSTGRES_DB` を `marvis` のデフォルトから変更している場合は、`.env` の値に置き換えてください。データは `marvis_pgdata` という名前付きボリュームにあり、`docker compose down` では消えませんが、`down -v` では消えます。

### migration は自動で実行されます

[ステップ1](#1-marvis-を起動する)と同じく、バックエンドコンテナはトラフィックを受け付ける前に起動時に `./migrate up` を実行します（`docker/entrypoint.sh`）。個別のアップグレードコマンドはありません — 新しいイメージを立ち上げること自体が migration のステップです。様子を見るには:

```bash
docker compose -f docker-compose.selfhost.yml logs -f backend
```

migration は backend の起動時に自動で実行されます。過去データのバックフィルが必要な migration（103 など）も、バックフィルまで自動で完了します。ごくまれに自動バックフィルが `refusing to drop legacy daily rollups` で失敗することがあります。対処は[トラブルシューティング](/troubleshooting#migration-103-の失敗)を参照してください。

### `/health` ではなく `/readyz` で検証する

`/health` は **liveness** プローブで、プロセスが生きている限り `{"status":"ok"}` を返します — migration が失敗していても同じです。`/readyz`（`server/cmd/server/router.go` で登録された `readyHandler`、`/healthz` はそのエイリアス）はデータベースと適用済み migration の集合をチェックするため、失敗したアップグレードを捕捉できるのはこちらです。

```bash
curl -s localhost:13840/readyz
# {"status":"ok","checks":{"db":"ok","migrations":"ok"}}
```

HTTP 200 かつ両方のチェックが `ok` でない場合、新しいバージョンは migration を完了していません。トラフィックを流す前にバックエンドのログを確認してください。

### Kubernetes

Helm には独自のアップグレード経路があります。values ファイルで `images.backend.tag` / `images.frontend.tag` に目的のリリースを設定し、`helm upgrade` を実行してください。タグを変えると Pod スペックが変わるため、Kubernetes が新しいイメージを取得して Deployment をロールします — これが確実な経路です。

`kubectl -n marvis rollout restart` はそれ単体ではアップグレードになりません。チャートは `pullPolicy: IfNotPresent` を同梱しているため（`deploy/helm/marvis/values.yaml`）、そのタグをすでにキャッシュしているノードでは古いイメージが再利用され、restart しても何も変わりません — `MARVIS_IMAGE_TAG` の固定と同種の落とし穴です。浮動タグでこの方法を使いたい場合は、先に `images.backend.pullPolicy` / `images.frontend.pullPolicy` を `Always` に設定してください。リポジトリの [Self-hosting guide](https://github.com/yunboom/marvis/blob/main/SELF_HOSTING.md#kubernetes-deployment-alternative) を参照してください。

<Callout type="warning">
`docker compose down` は `pgdata` と `backend_uploads` を保持します。`-v` を付けると、データベースを含むこれらのボリュームが削除されます。インスタンスを消去するつもりがない限り、`docker compose down -v` を実行しないでください。
</Callout>

## よくある問題

| 症状 | まず確認すること |
|---|---|
| `/readyz` が `ok` を返さない | `docker compose -f docker-compose.selfhost.yml logs backend postgres` を実行する。 |
| 認証コードが届かない | コードを一度リクエストし、backend のログで `Verification code` を探す。 |
| `setup self-host` が server に到達できないと報告する | 実行用コンピュータから `https://api.example.com/health` をリクエストし、DNS、TLS、リバースプロキシがすべて到達可能か確認する。404 が返る場合、プロキシが `/health` をこのパスを転送しない古い web リリースに向けているため、backend へ直接ルーティングすること（[トラブルシューティング](/troubleshooting#marvis-setup-がサーバーに到達できないと報告する)）。 |
| デーモンが `Agents` を表示しない | AI コーディングツールが `PATH` にありログイン済みであることを確認し、`marvis daemon restart` を実行する。 |
| タスクがキューにとどまり続ける | `marvis daemon status` を実行し、デーモンが起動していてワークスペースに接続していることを確認する。 |

その他のケースは[トラブルシューティング](/troubleshooting)を参照してください。
