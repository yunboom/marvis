Marvis Desktop est disponible pour macOS, Windows et Linux. Il utilise le même compte et les mêmes données d'espace de travail que l'application web, mais il gère automatiquement le daemon sur votre machine et conserve un ensemble d'onglets distinct pour chaque espace de travail.

## Desktop et web

| | Web | Desktop |
| --- | --- | --- |
| Comment l'ouvrir | Navigateur | Installer l'application de bureau |
| Onglets par espace de travail | Utilise les onglets du navigateur | Chaque espace de travail conserve ses propres onglets |
| Daemon | Installer et démarrer le CLI séparément | Démarré automatiquement par l'application après la connexion |
| Mises à jour | Actualiser la page | Mises à jour via l'application de bureau |

Le web est plus pratique pour un coup d'œil rapide ou sur un ordinateur partagé.

Vous pouvez être connecté aux deux en même temps. Tant qu'ils se connectent au même service Marvis, les données qu'ils affichent sont partagées.

## Installation

Choisissez le programme d'installation correspondant à votre système d'exploitation et à l'architecture de votre processeur sur la [page de téléchargement de Marvis](https://marvis.ai/download) :

| Plateforme | Programme d'installation |
| --- | --- |
| macOS | `.dmg` |
| Windows | `.exe` |
| Linux | `.AppImage`, `.deb` ou `.rpm` |

Après l'installation, [connectez Desktop à un serveur Marvis](#se-connecter-à-un-serveur) et connectez-vous. Une fois connecté, Desktop démarre son propre CLI Marvis intégré et détecte les outils de codage IA déjà installés sur la machine.

<Callout type="info">
Le CLI intégré à Desktop sert uniquement au runtime géré par l'application. Si vous voulez aussi exécuter des commandes comme `marvis issue` dans un terminal, installez le CLI séparément en suivant l'[étape 2 du démarrage rapide](/cloud-quickstart#2-connectez-un-ordinateur).
</Callout>

## Onglets de Desktop

Desktop enregistre les onglets par espace de travail. Par exemple, si vous ouvrez trois tâches dans l'espace de travail A puis passez à l'espace de travail B, vous voyez les onglets propres à B ; revenez à A et les trois onglets précédents sont toujours là.

Une même ressource ne s'ouvre qu'une seule fois dans l'espace de travail courant. Les onglets peuvent être réordonnés, épinglés et fermés, et chacun conserve son propre historique de navigation avant/arrière et sa position de défilement. Cliquer sur un lien de l'application pour ce déploiement, ou le coller, l'ouvre directement dans un onglet au lieu de basculer vers le navigateur.

La déconnexion efface tous les onglets enregistrés sur la machine : la personne suivante qui se connecte ne voit jamais les pages laissées par le compte précédent.

## Daemon intégré

Après la connexion, Desktop crée un profil CLI dédié au service Marvis courant et l'utilise pour démarrer le daemon. Le profil se trouve ici :

```text
~/.marvis/profiles/desktop-<host>/
```

Il ne lit ni n'écrase jamais le profil par défaut que vous utilisez dans le terminal. Si vous démarrez aussi manuellement un autre daemon, Marvis les affiche comme des runtimes distincts.

Vous pouvez consulter l'état et les journaux du runtime dans les paramètres de Desktop. Si un outil n'est pas détecté, vérifiez d'abord qu'il fonctionne dans un terminal ordinaire et qu'il est connecté, puis redémarrez le daemon de Desktop.

## Mettre à jour Desktop

La mise à jour automatique est activée par défaut. L'application recherche et télécharge les nouvelles versions en arrière-plan ; une fois une version téléchargée, vous pouvez redémarrer pour l'installer immédiatement ou la laisser s'installer à la prochaine fermeture. Vous pouvez aussi désactiver les vérifications automatiques ou rechercher manuellement de nouvelles versions dans **Paramètres → Mises à jour**.

Les mises à jour sont distribuées par système d'exploitation et par architecture de processeur :

- Windows arm64 et macOS x64 (Intel) utilisent chacun leur propre flux de mise à jour ;
- toutes les autres architectures utilisent le flux par défaut ;
- l'application sélectionne automatiquement le bon flux de mise à jour — aucun choix manuel n'est nécessaire ;
- sous Linux, la mise à jour automatique ne fonctionne qu'avec `.AppImage` ; mettez à jour `.deb` et `.rpm` en installant un nouveau paquet par-dessus l'ancien ;
- si la mise à jour automatique échoue, réinstallez de la même façon par-dessus avec le programme d'installation correspondant, disponible sur la page de téléchargement.

## Se connecter à un serveur

Desktop se connecte au serveur Marvis, c'est-à-dire au backend. L'application web est facultative.

### Premier lancement

Sans serveur configuré, Desktop affiche **Se connecter à un serveur Marvis**.

1. Choisissez un serveur sous **Serveurs du réseau local**, ou saisissez une adresse. L'adresse par défaut est `http://marvis.local:13840`.
2. Pour une adresse, cliquez sur **Tester la connexion**. Desktop affiche le nom et la version du serveur, ou la raison de l'échec.
3. Cliquez sur **Continuer**, vérifiez l'adresse sur la page de confirmation, puis cliquez sur **Se connecter**.
4. Connectez-vous.

La liste se met à jour quand des serveurs apparaissent ou disparaissent. **Rechercher à nouveau** relance la recherche. L'ordinateur et le serveur doivent être sur le même réseau. Un serveur qui tourne sur cet ordinateur porte l'étiquette **Cet ordinateur**. Un serveur dont la version est trop ancienne est affiché mais ne peut pas être sélectionné.

Desktop attend votre confirmation avant de se connecter et n'ouvre jamais de session seul. Un serveur en HTTP n'est pas chiffré, et la page de confirmation le signale.

Desktop enregistre le serveur choisi dans `server.json`, dans son dossier de données d'application :

| Plateforme | Chemin |
| --- | --- |
| macOS | `~/Library/Application Support/Marvis/` |
| Linux | `~/.config/Marvis/` |
| Windows | `%APPDATA%\Marvis\` |

### Changer de serveur

Ouvrez **Paramètres → Cet appareil → Serveur**. La page affiche :

- le serveur actuel, avec son nom, son adresse et l'état de la connexion ;
- les autres serveurs trouvés sur le réseau local, chacun avec **Changer** ;
- un champ **Autre adresse**, avec **Tester la connexion** et **Changer**.

Changer de serveur déconnecte le compte actuel. Desktop demande confirmation, enregistre le nouveau serveur et ouvre la page de connexion. Le daemon intégré utilise automatiquement le profil du nouveau serveur.

Ce réglage ne concerne que cet ordinateur.

### Connexion interrompue

- Quand le serveur ne répond plus, une bannière en haut de la zone principale indique que la connexion est perdue et que Desktop se reconnecte.
- Après plusieurs échecs, la bannière indique que le serveur est injoignable et propose **Réessayer** et **Changer de serveur**. Desktop continue de vérifier et repasse en ligne dès que le serveur revient.
- Un serveur choisi dans la liste du réseau local est enregistré par son adresse IP. Quand cette adresse ne répond plus et que le même serveur, reconnu par son ID d'instance, apparaît sur le réseau local avec une nouvelle IP, Desktop passe à la nouvelle adresse et indique qu'il s'est reconnecté.
- Quand un autre serveur répond à l'adresse enregistrée, Desktop affiche **Un autre serveur répond à cette adresse** et ne change pas de serveur seul. Choisissez **Continuer à attendre** ou **Changer de serveur**.

### Sans application web

Quand le serveur n'a pas d'adresse web, ou que cette adresse est `localhost`, Desktop le traite comme un serveur sans application web :

- la page de connexion masque le bouton Google. Le bouton Feishu reste affiché quand la connexion Feishu est configurée sur le serveur et que son adresse de rappel pour Desktop est enregistrée dans la console développeur Feishu, voir [Desktop et application web](/self-host-quickstart#desktop-et-application-web). Desktop ouvre alors la connexion Feishu dans le navigateur et revient dans l'application à la fin. Sinon, seule la connexion par code e-mail reste ;
- **Copier le lien** produit un lien `marvis://open?...`, qui s'ouvre dans Desktop sur tout ordinateur où Desktop est installé et connecté au même serveur.

## Préconfigurer le serveur avec desktop.json

Un administrateur peut préconfigurer le serveur d'un ordinateur. Desktop ne lit cette configuration que tant qu'aucun serveur n'a été choisi dans l'application. Il se connecte sans afficher la page de connexion et n'écrit jamais dans le fichier.

Créez `desktop.json` dans le répertoire `.marvis` de votre répertoire personnel :

| Plateforme | Chemin |
| --- | --- |
| macOS | `/Users/<you>/.marvis/desktop.json` |
| Linux | `/home/<you>/.marvis/desktop.json` |
| Windows | `C:\Users\<you>\.marvis\desktop.json` |

Ce sont les emplacements par défaut — si votre répertoire personnel a été déplacé ou redirigé, utilisez son chemin réel.

```json
{
  "schemaVersion": 1,
  "apiUrl": "https://api.example.com"
}
```

<Callout type="warning">
Il ne s'agit **pas** du `~/.marvis/config.json` du CLI, et les noms de clés diffèrent : le CLI utilise `server_url`, Desktop utilise `apiUrl`. Desktop ne lit jamais la configuration du CLI — il gère un profil de daemon distinct dans `~/.marvis/profiles/desktop-<host>/`. Modifier `config.json` ne change pas le serveur auquel Desktop se connecte.
</Callout>

`apiUrl` est l'adresse publique du backend ; elle est obligatoire et doit utiliser `http` ou `https`. Les deux autres URL peuvent être omises — Desktop les déduit automatiquement :

- `wsUrl` : remplace le schéma de `apiUrl` par `ws` ou `wss` et ajoute `/ws` au chemin ;
- `appUrl` : retire le préfixe `api.` lorsque l'hôte commence par `api.` et comporte au moins trois niveaux (`api.example.com` → `example.com`) ; sinon, elle reste identique à `apiUrl`.

Une configuration préconfigurée comporte toujours une adresse web, déduite quand `appUrl` est omis. Pour utiliser Desktop sans application web, choisissez plutôt le serveur dans l'application.

En général, `apiUrl` seul suffit. Ne les définissez explicitement que si la déduction ne correspond pas à votre déploiement ; les trois cas courants :

- l'application web et l'API sont sur des domaines différents ;
- le WebSocket est déployé séparément ;
- l'hôte ne suit pas la convention de retrait du préfixe (les hôtes à deux niveaux comme `api.local` conservent leur préfixe).

```json
{
  "schemaVersion": 1,
  "apiUrl": "https://api.example.com",
  "appUrl": "https://app.example.com",
  "wsUrl": "wss://ws.example.com/socket"
}
```

Redémarrez Desktop après l'enregistrement — le fichier n'est lu qu'une fois, au démarrage. Les deux modes d'échec se manifestent différemment, ce qui est le moyen le plus rapide de les distinguer :

- **Fichier introuvable** (mauvais répertoire, ou nom de fichier qui n'est pas exactement `desktop.json`) — Desktop affiche la page de connexion et aucune erreur. Donc, si Desktop demande toujours de choisir un serveur sans erreur de configuration, le fichier ne se trouve pas là où Desktop le cherche.
- **Fichier trouvé mais invalide** (JSON, version ou URL) — Desktop affiche une erreur de configuration.

Supprimez le fichier et redémarrez pour revenir à la page de connexion. Si un serveur a été choisi dans l'application, supprimez aussi `server.json` dans le dossier de données de l'application.

<Callout type="warning">
Desktop ne peut se connecter qu'à des adresses joignables à la fois depuis le navigateur et depuis la machine d'exécution. Si une instance auto-hébergée distante n'utilise pas HTTPS ou ne fait pas passer le WebSocket par son proxy, Desktop ne peut pas établir de connexion ; consultez le [démarrage rapide en auto-hébergement](/self-host-quickstart#3-choisir-le-mode-daccès) pour la configuration complète.
</Callout>

### Windows : vérifier le nom et l'encodage du fichier

Deux comportements par défaut des éditeurs Windows produisent silencieusement un fichier que Desktop ne peut pas utiliser :

- **Le Bloc-notes ajoute `.txt`.** Enregistrer sous `desktop.json` peut produire `desktop.json.txt`, que Desktop considère comme introuvable. Activez l'affichage des extensions de noms de fichiers dans l'Explorateur de fichiers, ou choisissez *Tous les fichiers* dans la boîte de dialogue d'enregistrement. Pour voir le vrai nom du fichier, exécutez `Get-ChildItem "$env:USERPROFILE\.marvis" -Filter "desktop.json*"` dans PowerShell — la colonne `Name` doit indiquer exactement `desktop.json`.
- **La redirection PowerShell écrit en UTF-16 ou avec un BOM.** `> desktop.json` et `Out-File` peuvent produire un encodage impossible à analyser, qui se traduit par une erreur de configuration.

Pour éviter ces deux problèmes, créez le fichier depuis PowerShell en une seule étape :

```powershell
$dir = "$env:USERPROFILE\.marvis"
New-Item -ItemType Directory -Force $dir | Out-Null
$json = @'
{
  "schemaVersion": 1,
  "apiUrl": "https://api.example.com"
}
'@
[System.IO.File]::WriteAllText("$dir\desktop.json", $json)
```

## Windows Defender signale Marvis comme un virus

**Symptôme** : Sécurité Windows signale une menace telle que `Trojan:Script/Wacatac.B!ml` et met en quarantaine un fichier de l'installation de Desktop. L'élément concerné est normalement le CLI intégré, et non l'exécutable de l'application :

```text
C:\Users\<you>\AppData\Local\Programs\@marvisdesktop\resources\app.asar.unpacked\resources\bin\marvis.exe
```

**Il s'agit d'un faux positif.** Le suffixe `!ml` signifie que le verdict provient des heuristiques d'apprentissage automatique de Defender, et non d'une signature de logiciel malveillant. Les builds Windows de Marvis ne sont pas encore signées avec Authenticode, et un binaire non signé tout juste publié, qui lance des processus en arrière-plan et ouvre des connexions réseau, correspond exactement au profil que ces heuristiques jugent suspect. Chaque artefact Windows est construit par GitHub Actions à partir du code source public de ce dépôt.

**Vérifiez par vous-même** — chaque release GitHub publie un fichier `checksums.txt` couvrant toutes les archives du CLI :

```powershell
Get-FileHash .\marvis-cli-<version>-windows-amd64.zip -Algorithm SHA256
```

Comparez l'empreinte obtenue avec la ligne correspondante de `checksums.txt` dans la [dernière release](https://github.com/yunboom/marvis/releases/latest).

**Comment corriger** :

1. **Restaurez le fichier mis en quarantaine** — Sécurité Windows → *Protection contre les virus et menaces* → *Historique de protection* → sélectionnez l'élément Marvis → *Actions* → *Restaurer*.
2. **Ajoutez une exclusion** pour qu'il ne soit plus mis en quarantaine — *Protection contre les virus et menaces* → *Gérer les paramètres* → *Exclusions* → *Ajouter une exclusion* → *Dossier*, et ajoutez les deux dossiers suivants :
   - `%LOCALAPPDATA%\Programs\@marvisdesktop`
   - `%APPDATA%\Marvis`

   Les deux chemins sont nécessaires : lorsque le CLI intégré disparaît, Desktop télécharge un remplaçant dans `%APPDATA%\Marvis\bin` ; exclure uniquement le dossier d'installation vous enferme donc dans une boucle où le remplaçant est lui aussi mis en quarantaine.
3. **Signalez le faux positif à Microsoft** sur [Microsoft Security Intelligence — soumettre un fichier](https://www.microsoft.com/en-us/wdsi/filesubmission), en choisissant *Software developer* et *Incorrectly detected as malware*. C'est ce qui permet de retirer la détection pour tous les utilisateurs, généralement en quelques jours.

<Callout type="warning">
N'ajoutez ces exclusions que si vous avez installé Marvis depuis la [page de téléchargement](https://marvis.ai/download) ou les [releases GitHub](https://github.com/yunboom/marvis/releases) et que la somme de contrôle correspond. Une exclusion désactive la protection en temps réel pour tout le contenu de ce dossier.
</Callout>
