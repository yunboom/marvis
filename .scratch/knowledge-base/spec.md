# Spec：知识库

状态：ready-for-agent
术语见 `GLOSSARY.md`「知识库」一节；取舍见 `docs/adr/0002-knowledge-base.md`；实现中自行决定的事项见同目录 `decisions.md`。

## Problem Statement

团队在 Marvis 里用任务和对话协作，产生的知识散落在任务描述、评论、对话里，没人整理；智能体每次接活都从零了解系统、业务规则和流程。人写的 wiki 维护成本随规模增长，很快过时。团队需要一个由智能体按 Karpathy LLM Wiki 模式持续维护、由人审核把关的知识库，并且能被智能体在干活时直接使用。

## Solution

侧栏「AI 团队」里、Skills 上方新增「知识库」。一个工作区可以有多个知识库，全部放在同一个 git 仓库里按目录隔离，用一份内置的综合 schema（OKF v0.2 页面 + 论断文件）。成员阅读页面、对句子或整页提批注；批注、沉淀资料、保鲜、知识合并都在知识库页里开一个和维护智能体的会话完成；智能体和成员的所有改动都产出变更请求，进入全局待审核队列，由 owner / admin 合并。内置的每日知识沉淀自动化每天汇总任务、评论和对话，产出一个变更请求。`marvis kb` 命令行覆盖知识库的全生命周期（删除除外），智能体在任何任务里都能通过它查阅和维护知识库。

## User Stories

### 浏览
1. 作为成员，我想在侧栏 Skills 上方看到「知识库」，以便随时进入。
2. 作为成员，我想在知识库页顶部切换工作区里的多个知识库，以便查看不同领域的知识。
3. 作为成员，我想按页面类型（实体、概念、操作手册、决策、综合分析、来源、问答）浏览页面树，以便快速定位。
4. 作为成员，我想按领域标签（开发、测试、产品）筛选页面树，以便只看和我相关的内容。
5. 作为成员，我想看到页面的类型、领域、是否已核实及核实人和时间，以便判断可信度。
6. 作为成员，我想看到页面上「N 条论断可能过期」的提示，以便知道哪些内容需要谨慎使用。
7. 作为成员，我想悬停引用编号查看来源（任务、代码、文档、对话），以便追溯依据。
8. 作为成员，我想看到引用他人对话的来源只显示「某人与某智能体的对话 · 日期」且我打不开，以便保护他人对话隐私。
9. 作为成员，我想看到页面的反向链接，以便顺着关联继续阅读。
10. 作为成员，我想搜索知识库，以便直接找到答案。
11. 作为成员，我想在搜索无结果时按回车把问题记为知识缺口，以便以后被补齐。

### 批注
12. 作为成员，我想选中页面里的一句话写批注，以便指出具体哪里不对。
13. 作为成员，我想对整页写批注，以便提出不针对某句话的意见。
14. 作为成员，我想在页面右侧看到本页所有未处理的批注，以便了解别人提过什么。
15. 作为成员，我想在批注列表按状态（待处理、处理中、已解决、不处理）筛选，以便管理队列。
16. 作为成员，我想把批注标为「不处理」，以便清理误报。
17. 作为成员，我想勾选多条批注一次交给智能体处理，以便统一纠错。
18. 作为成员，我想在页面被改写后，原先锚定的句子找不到时批注自动变成页面批注，以便意见不会丢失。
19. 作为成员，我想看到批注关联的变更请求编号，以便跟进处理结果。
20. 作为成员，我想看到智能体保鲜时发现的问题也以批注出现，以便先过滤误报再交给智能体。

### 智能体会话
21. 作为成员，我想发起批注纠错、沉淀资料、保鲜、知识合并、补齐缺口时打开一个和维护智能体的会话，以便边看边纠正它。
22. 作为成员，我想会话的第一条消息自动写好「遵循某知识库的 AGENTS.md 完成……」并附上下文，以便不用自己写提示词。
23. 作为成员，我想在会话右侧实时看到被改动的文件，以便了解进度。
24. 作为成员，我想在会话中途停止智能体，以便及时止损。
25. 作为成员，我想在会话结束后继续追加意见，让智能体更新同一个变更请求，以便迭代。
26. 作为成员，我想在会话里看到产出的变更请求并一键去审核，以便衔接审核。
27. 作为成员，我想在第一次对某个没有维护智能体的知识库发起操作时先选维护智能体，以便后续默认使用它。
28. 作为成员，我想会话不出现在「我的对话」里，以便对话列表保持干净。
29. 作为成员，我想沉淀资料时可以上传文件、贴链接、选任务、选我自己的对话，以便从各种来源入库。
30. 作为成员，我想知识合并时可以选择合并重复页面（可跨库）或把一个库合并进另一个库，以便清理重复。

### 变更请求与审核
31. 作为成员，我想手动编辑页面后提交成变更请求，以便改动也经过审核。
32. 作为 owner / admin，我想在全局「待审核」队列看到所有知识库的未合并变更请求，以便集中审核。
33. 作为成员，我想在侧栏「知识库」上看到待审核数量，以便知道有事待办。
34. 作为审核人，我想看到变更请求的来源（批注纠错、沉淀、保鲜、知识合并、补齐缺口、每日沉淀、手动编辑、回滚）、作者和涉及的知识库，以便判断优先级。
35. 作为审核人，我想看到智能体自查的摘要、风险和影响文件数，以便快速评估。
36. 作为审核人，我想看到 lint、stale、能否合并三项检查结果，以便发现明显问题。
37. 作为审核人，我想按知识库分组看 diff，以便跨库改动也清楚。
38. 作为审核人，我想点行号写行评论，以便把具体修改意见留给智能体。
39. 作为 owner / admin，我想合并变更请求，以便改动生效。
40. 作为 owner / admin，我想合并自己的变更请求，以便独自维护时不被卡住。
41. 作为审核人，我想关闭变更请求，并让关联批注退回待处理，以便重来。
42. 作为审核人，我想在变更请求与主线冲突时看到提示并让智能体基于主线更新，以便解决冲突。
43. 作为普通成员，我想看到合并按钮不可用并提示需要 owner 或 admin，以便知道该找谁。
44. 作为成员，我想从变更请求回到产出它的会话，以便看智能体怎么想的。

### 历史与关系
45. 作为成员，我想看到已合并的变更历史，以便了解知识库怎么演变。
46. 作为成员，我想回滚某次已合并的变更（生成新的变更请求），以便撤销错误。
47. 作为成员，我想看关系图，悬停高亮关联、点击打开页面、孤儿页虚线显示，以便发现结构问题。
48. 作为成员，我想看到知识缺口列表并交给智能体补齐，以便知识库越来越全。

### 管理
49. 作为成员，我想新建知识库：填名称、描述、维护智能体，使用内置 schema，以便马上可用。
50. 作为成员，我想让智能体在会话里帮我拟知识库的 schema 和 purpose，确认后直接创建，以便定制。
51. 作为创建者或 owner / admin，我想修改知识库名称、描述、维护智能体，以便保持准确。
52. 作为 owner / admin，我想删除知识库，并在确认前看到会一并关闭的批注和变更请求数量，以便知情决定。
53. 作为 owner / admin，我想删除最后一个知识库时被告知每日知识沉淀会停用，以便知道后果。
54. 作为成员，我想下载知识库 zip，以便离线查看或用 Obsidian 打开。
55. 作为新工作区的创建者，我想工作区一创建就有一个「团队知识库」，以便立刻开始用。

### 每日知识沉淀
56. 作为 owner / admin，我想在自动化里看到带锁标的「每日知识沉淀」，以便知道它是内置的。
57. 作为 owner / admin，我想配置每日知识沉淀的执行者、时间和时区，以便按团队节奏运行。
58. 作为 owner / admin，我想启用、停用每日知识沉淀，但不能删除它，以便它不会被误删。
59. 作为 owner / admin，我想在没有知识库时看到每日知识沉淀不能启用，以便不浪费 token。
60. 作为 owner / admin，我想立即运行一次每日知识沉淀并看到运行记录和产出的变更请求，以便验证效果。
61. 作为成员，我想每日知识沉淀只读取执行智能体所在运行时主人自己的对话，以便他人对话不被读取。

### 命令行与智能体
62. 作为智能体，我想在任何任务里知道有哪些知识库及其描述，以便自己决定要不要查阅。
63. 作为智能体，我想用 `marvis kb list/get` 查看知识库，以便选择。
64. 作为智能体，我想用 `marvis kb page list/get` 和 `marvis kb search` 查阅页面，以便获取上下文。
65. 作为智能体，我想用 `marvis kb clone` 把仓库拉到本地，修改后用 `marvis kb change create` 推分支并建变更请求，以便提交改动。
66. 作为智能体，我想在创建变更请求时立刻得知冲突的文件和行，以便自己重做。
67. 作为智能体，我想用 `marvis kb change get --comments` 读取审核意见，用 `marvis kb change update` 更新同一个变更请求，以便迭代。
68. 作为智能体，我想用 `marvis kb lint` 检查死链、孤儿页、缺字段、引用失效和 index 不一致，以便提交前自查。
69. 作为智能体，我想用 `marvis kb stale` 按论断比对证据版本找出可能过期的内容，以便保鲜。
70. 作为智能体，我想用 `marvis kb annotate add/list` 记录和查看批注，以便保鲜发现的问题进入队列。
71. 作为智能体，我想用 `marvis kb gap add/list` 记录知识缺口，以便后续补齐。
72. 作为每日沉淀智能体，我想用 `marvis kb sources --since` 分页拿到时间段内的任务、评论和对话精简内容，每页不超过上下文窗口的 60%、最多 10 页，以便不撑爆上下文。
73. 作为管理员，我想通过 `marvis kb digest get/update/enable/disable/run` 管理每日知识沉淀，以便脚本化运维。
74. 作为成员，我想 CLI 不提供删除知识库，以便误操作不可能发生在命令行。
75. 作为成员，我想用 `marvis kb merge` 发起知识合并，以便在命令行完成合并。

## Implementation Decisions

- **数据模型**（新表，无外键，依赖清理在应用代码里做）：
  - `knowledge_base`：工作区、名称、slug（工作区内唯一，即仓库目录名）、描述、维护智能体、创建者、时间。
  - `knowledge_change_request`：工作区、编号（工作区内自增，显示为 #N）、标题、来源、作者（成员或智能体）、分支、基线 commit、状态（open / merged / closed）、是否冲突、冲突说明、自查摘要、风险、合并 commit、关联会话、时间。涉及的知识库由 diff 推出，不单独存。
  - `knowledge_change_comment`：变更请求、文件路径、行号、作者、内容、时间。
  - `knowledge_annotation`：工作区、知识库、页面路径、句子锚点（原文与前后文）、内容、作者、状态（pending / processing / resolved / dismissed）、关联变更请求、时间。
  - `knowledge_gap`：工作区、问题、来源（search_miss / agent）、状态（open / processing / filled）、时间。
  - `knowledge_session`：会话与隐藏 agent 的对应关系、操作类型（fix / ingest / fresh / merge / gap / create / rebase）、知识库、发起人。
  - autopilot 新增 `system_key`，取值 `knowledge-digest` 时删除接口拒绝，启用时要求工作区至少有一个知识库。
  - 所有词表值（来源、状态、操作类型）在 Go 和 TS 各定义一次具名常量。
- **仓库层**（新的内部包）：初始化工作区 bare repo、写入内置 schema、读文件树与文件、列提交、计算分支 diff、`merge-tree` 冲突检测与合并、回滚（反向应用某个合并）、打包 zip；提供 smart HTTP handler。对外接口是「工作区 → 仓库」的窄接口，handler 不直接拼 git 命令。
- **页面解析**（同一内部包或独立包）：解析 frontmatter（OKF v0.2 字段）、切分句子锚点、提取 `[^n]` 脚注与来源、计算反向链接和关系图边、读取 `.claims/`。CLI 的 lint / stale 复用同一套解析。
- **HTTP API**（工作区作用域，`/api/knowledge/...`）：知识库增删改查（删除仅 owner/admin）、页面树与页面、搜索（记录未命中缺口）、批注增查改、缺口增查、变更请求列表 / 详情（含分组 diff 和评论）/ 创建 / 更新 / 合并 / 关闭 / 行评论、历史与回滚、关系图、zip 下载、会话创建、每日知识沉淀配置与运行、sources 分页；git smart HTTP 挂在同一前缀下。所有响应在前端经 zod schema + `parseWithFallback` 解析。
- **权限**：完全沿用 owner / admin / member + 创建者模式：查看、批注、发起、手动编辑、新建知识库是全体成员；改库设置是 owner/admin 或创建者；合并、删除库、每日知识沉淀配置是 owner/admin。
- **实时事件**：`knowledge:changed`（知识库、变更请求、批注、缺口变更）推送给工作区，前端失效对应查询。
- **meta-skill**：daemon 注入的说明里新增一节 `marvis kb` 用法和知识库列表（名称、slug、描述），智能体按描述自行决定是否使用。
- **知识库会话**：见 decisions.md #4。会话首条消息按「遵循知识库「X」的 AGENTS.md，完成……」生成，指令要求智能体提交前运行 lint、过滤敏感信息、在变更请求里写自查摘要和风险。
- **每日知识沉淀**：autopilot `run_only`，系统 `system_key`，描述里写明流程；执行时智能体调用 `marvis kb sources` 获取「上次运行以来」的数据，为所有有改动的库产出一个变更请求。对话只取任务 token 对应用户（运行时主人）自己的会话，且只取 `kind=user` 的 agent。
- **sources 分页**：按 `--context-window` 估算字符预算（窗口 token × 60% × 每 token 约 2 个中文字符的保守系数），最多 10 页，超出返回 `truncated: true` 和剩余数量。
- **内置 schema**：`AGENTS.md`、`purpose.md`、`index.md`、`log.md`、`overview.md`、`raw/`、`wiki/{entities,concepts,howtos,decisions,syntheses,sources,queries}/`、`.claims/`；工作区创建时生成「团队知识库」（slug `team`）。
- **前端**：知识库页（页面 / 待审核 / 批注 / 缺口 / 关系图 / 历史 / 设置标签）、会话面板（左对话右预览，复用聊天 hooks）、新建 / 沉淀 / 合并 / 删除 / 选择智能体弹窗；自动化列表与详情识别系统自动化。web 和 desktop 都接路由。

## Testing Decisions

- 好的测试只验证外部行为：HTTP 状态码与响应体、仓库里的文件与提交、CLI 输出，不断言内部函数调用。
- **主接缝：HTTP API**（DB-backed handler 测试，`testutil.Call`）。覆盖：知识库 CRUD 与权限、删除级联关闭批注和变更请求、变更请求创建 / 冲突 / 合并 / 关闭 / 行评论、批注状态流转、缺口记录、每日知识沉淀不可删除与无库不可启用、sources 分页与对话范围。先例：`autopilot` 与 `skill` 的 handler 测试。
- **仓库层**：在临时目录上验证初始化、diff、merge-tree 冲突、回滚、pre-receive 拒绝推主线。先例：daemon 里使用真实 git 的测试。
- **解析与 CLI 检查**：lint / stale / 句子切分 / sources 预算用表驱动测试。先例：`server/internal/skill/frontmatter_test.go`。
- **前端**：core 的 schema 畸形响应测试；views 的知识库页组件测试覆盖页面阅读、批注、审核合并按钮的权限态。先例：skills 页测试、`packages/core/api/schema` 测试。
- 不跑真实智能体；会话测试只验证隐藏 agent 与会话的创建和首条消息。
